Lucid.

AI executes. The human designs, tests and secures.

Lucid coding is vibe coding with the human awake: the same speed, but knowing at every moment what the agent is doing, and steering it. It is for developers who already work with coding agents and want to do it with method. It grew out of a year of daily practice, measured over more than 21,000 real prompts. Its ritual word is the one typed most in them: “proceed” (from the Spanish «proceda»).

1 · Manifesto

Five values

  1. Architecture decided by humansovercode the AI improvises
  2. Templates and repos that already workoverbuilding from scratch
  3. Continuous execution, one change at a timeoverlong plans with no commits
  4. Product tested by handoverautomated coverage nobody looked at
  5. Security reviewed by a personoverblind trust in the AI

There is value in the items on the right, and we use them: the AI writes code and tests. But when they conflict, the items on the left win.

2 · Pillars

Seven pillars split the work between human and AI

They are the backbone of the method. Everything that follows exists to hold them up. They are remembered by the five letters of LUCID, which work the same in English and Spanish.

LLead the designLiderar el diseño · pillar 0
UUse what worksUsar lo que funciona · pillars I and 2
CCommit & controlCommit y control · pillars 1 and 5
IInspect everythingInspeccionar todo · human or agent · pillar 3
DDefendDefender · pillar 4
  1. I

    Foundations · U

    Start from code and architectures that already exist and that the developer already knows. Hand the agent ready-made repos and tools that are already built, so it uses code templates that already work instead of doing everything from scratch.

  2. 0

    Architecture · L

    The soul of the code. This is where the developer brings the vision: what needs to be done and how. It is where their creativity lives, and it is not delegated.

    human
  3. 1

    Proceed · C

    Always forward with the AI. In execution, the AI is in charge: it does everything it can, terminal and browser included, and never hands back work it could do itself.

    AI
  4. 2

    Method · C

    Ready-made method templates, one per type of build, to guide the AI. They translate into concrete, linear rules that form the system's hard harness. Every error that repeats becomes one more rule.

    guided AI
  5. 3

    QA · I

    Intensive product QA, mostly human: every element is tested separately and by hand. The AI automates only unit tests and controlled automations. The main techniques are driving the browser, debugging in a controlled way and using the CLI to simulate the user.

    human + AI
  6. 4

    Security · D

    This is where you still code “by hand”, and where all available review time goes. Building on a solid grounding in information security, the human chooses components and parameters according to the architecture, the costs and the business. The AI implements them first, along with the unit tests and simulations. At the end, the developer reviews the code by hand.

    Never delegated 100% to the AI.

    human
  7. 5

    Control & auditability · C

    In collaborative development, the team has to be able to see what each dev does with the AI. Session logs and the record of prompts given to agents are kept, together with the commit each one produced.

    A written policy defines how AI is used in the project: which tools and models are allowed, which data and credentials the agent may see, and what gets logged. That gives you traceability for audits, above all of code security and credential use.

    No log, no audit.

    team
3 · The agent

The agent lies, is lazy and is always sure of itself

Not out of malice: that is how it works. It is wrong with total confidence, takes shortcuts and declares done what it never checked. That is why the method starts from suspicion, not faith.

  1. 0

    Always be suspicious

    Everything the agent does or says is a hypothesis until you see the proof. Make it test, verify and check, especially on what matters. “Done” without evidence (test output, URL, deployed version) does not count.

  2. 1

    E2E and production, always

    Ask it to run the e2e tests and check production. That way it works with the context that matters, what is actually running, not with what it thinks it remembers.

  3. 2

    An adversary with a clean context

    Once there is a solid codebase, another agent attacks it: pushes back, hunts for bugs and flaws. It starts from a clean context, without the builder's conversation or justifications, and evaluates only against evaluation rules defined in advance.

    The agent that wrote the code defends its work. A new one has nothing to defend.

4 · The framework

Four levels, three human hats and one definition of done

Levels of work

The smallest unit is the Change: one prompt that ends in one commit. Changes make up sessions, sessions make up milestones, and milestones move the product forward.

Product

weeks to months

Seed → Proposal → MVP → Production → Polish → Operation → Retirement. The Proposal and the move to Production are always decided by the human.

Milestone

hours to dayscloses with a human gate

A visible result: an MVP, a feature in production, a security hardening.

Session

one topic · before compacting

Opens with Kickoff and ends with Wrap-up.

Change

minutes · prompt → commit

Generation, Integration, Evaluation and Debugging, all complete. Auditable by another AI.

Three events

Session start

Kickoff

sync with prod, read BACKLOG and STATUS, tell me in 3 lines where we are

The agent starts from what is deployed, not from its memory.

Session end

Wrap-up

let's wrap up
  1. E2E test of what was touched
  2. BACKLOG: done, pending, blocked
  3. New lesson into the rules
  4. commit, push, deploy and verified version
  5. 3-line summary
Milestone end · human

Gate

Adversarial agent review, manual test of every element, line-by-line security review if sensitive code was touched, and a decision: continue, fix or stop.

The milestone's repeated errors become rules or templates.

Between Kickoff and Wrap-up, the loop is simple: the agent proposes numbered options, the human answers by number and says “proceed”.

Roles

On a one-person team, the same developer wears all three human hats. What never happens is handing one of them to the AI.

Human

Architect

Chooses foundations and architecture, writes the invariants, prioritizes and decides at every gate.

Tester

Tests every element by hand: browser, CLI simulating the user, controlled debugging.

Security Guardian

Chooses security components and parameters and reviews all sensitive code by hand.

AI

Lead agent

Maintains BACKLOG and STATUS, proposes options, hands out and integrates branches.

Executor agents

Make changes within a template, one per branch, and close each one with a commit.

Adversarial agent

Attacks the code from a clean context with fixed evaluation rules: hunts for bugs, flaws and what the Guardian should read. It flags; it does not replace.

A change is done when…

  • it is committed on the right branch, with a message that explains why;
  • unit tests and controlled automations pass, and the agent showed the output, not just said they pass;
  • the adversarial agent found no open flaws;
  • the Tester tested it by hand, element by element;
  • if it touches security, the Guardian reviewed it line by line;
  • it is in production with an e2e test and a verified version;
  • BACKLOG and STATUS are up to date.

5 · Operating rules

What applies in every session

Rule 0 · the essential one

Bounded context

The agent always works under a context cap, and every change has to complete its GIED cycle within it:

GenerationIntegrationEvaluationDebugging

The stable rule: every change fits entirely before the first compaction. With today's models, around 200k tokens is usually enough. If a change does not fit, split it in two; if the session nears the cap, do a Wrap-up and open a new one.

Token management, measured: in the last month, context per turn was 25k tokens (median) and 50k (p90); only 10 sessions went past 200k. Still, there were 840 compactions, in 52% of sessions: they come from long sessions that pile up, not from big changes. Managing tokens means closing and reopening sessions on time, not asking for a bigger window.

  1. 1

    Short, direct prompts

    No filler. Anything permanent goes into the context file or a template, not into every message.

  2. 2

    One change per prompt, auditable

    Once the project structure is in place, each prompt asks for a single change, as narrow as possible. Another AI must be able to audit it by reading the prompt and the diff.

  3. 3

    Concrete references, never adjectives

    A URL, a repo of your own, the exact technical name and a test case. “Make it more modern” is not a request.

  4. 4

    Numbered options

    When facing a decision, the agent proposes 2 or 3 numbered paths and the human answers by number. “Proceed” always takes an object: proceed with what.

  5. 5

    Every prompt ends in a commit

    Few active branches, each with a clear purpose (a routine, an autopilot, an environment) and as little divergence as possible.

    With too many branches the agent gets confused: it goes by the branch description more than by the commits, and on top of that come merges and divergences it overlooks.

  6. 6

    Multi-agent = separate branches

    If there is more than one agent in the repo, each works on its own branch and its own isolated copy (worktree), no exceptions. They coordinate through files, not memory, and the lead or the human decides the merge. Only independent work is parallelized.

    Orchestration: the lead hands out bounded tasks; each subagent starts from a clean context and returns a summary, not a dump of files. Side tasks go to a fork so they do not block the main thread, and the lead integrates and verifies what comes back.

    Last month: 1,022 subagents launched (512 general-purpose, 339 forks, 69 explorers), 204 messages between agents and ~2,490 worktree operations.

  7. 7

    Credentials: defined, inventoried and rotatable

    Before starting, define which credentials the agent will use and how they reach it.

    • Environment variables are the go-to way to hand them over. To share them, use a cloud vault: most trustworthy providers offer a vetted one that meets security standards.
    • In development you can give the credential directly to the agent, accepting the risk, but with a strict inventory: which key, where it was used, who saw it. When moving to production, everything in the inventory gets rotated.
    • Tell the agent. Agents often refuse to log into websites or use credentials for automation, and hand the work back to the human. If the project is in development, the context file says so explicitly: “dev stage, inventoried test credentials, rotated before prod”. That avoids blockers and wasted time.

    Some agents have limits no instruction lifts, such as typing real passwords or making payments. For those, the agent gets everything ready up to that step and the human completes it.

  8. 8

    What worked twice becomes a skill

    Procedures repeated successfully are saved as templates or preloaded skills the agent loads (kickoff, wrap-up, deploy, browser QA, publishing). On the second successful use, it gets saved. The agent does not reinvent; it loads.

    Last month: ~9,000 browser actions, but only ~30 skill invocations and a single project skill on disk. The procedure was rewritten every session; that is the gap this rule closes.

  9. 9

    Model selection: most capable by default

    The main thread always uses the most capable model. Fast models only in subagents for search, exploration or bulk tasks whose output gets verified afterwards. Architecture, security, hard debugging and auditing never drop a tier.

    Last month: ~99% of 94,606 responses came from the top model and ~0.5% from a fast one, always in subagents.

7 · Getting started

Four weeks on a real project

Week 1

Set up

Create the five files, write the INVARIANTS, define environment variables, vault and credential inventory, and save the kickoff and wrap-up templates.

Weeks 2–3

Practice

Every prompt ends in a commit, every session closes before compacting and every milestone goes through the gate. Friction goes into the LOG.

Week 4

Measure

Count in your transcripts: compactions per session, “What's left?”, design corrections and prompts that end in a commit. Compare with before and adjust.

8 · Evidence

What worked best, with almost zero corrections afterwards: answering numbered options by number, asking for 3 proposals and picking one, giving a URL or a repo of your own as a reference, naming the exact technique with a test case, and turning every successful session into a written procedure.
